### Findings

#### 1. The profile command a failed run tells you to use ignores the manifest's `workdir:` and writes a second manifest - Friction

**Persona:** new developer, diagnosing their first deny in a git checkout.

**Transcript:** (manifest `build.manifest.yaml` at the checkout root: `entrypoint: ./src/build.sh`, `workdir: .`, `read: [./src]`, `exec: all`)
```
$ bento run build.manifest.yaml
cat: data/input.txt: No such file or directory
4 src/build.sh
.../proj/src/build.sh: 4: cannot create build/out.txt: Directory nonexistent
[bento] the script exited 2. ...
[bento] all you get. To see what it actually touches:
[bento]   bento profile "/tmp/.../proj/src/build.sh"
...
$ bento profile "/tmp/.../proj/src/build.sh" </dev/null
cat: data/input.txt: No such file or directory
wc: 'src/*.sh': No such file or directory
.../src/build.sh: 4: cannot create build/out.txt: Directory nonexistent
[bento] not proposing write access to "/tmp/.../proj/src/build" - no such directory exists on the host ...
[bento] the manifest grants read "/tmp/.../proj/src" - that is the entire directory the script runs from ...
[bento] wrote /tmp/.../proj/src/build.sh.manifest.yaml - review it, then run `bento validate ...`
[bento] the proposal is incomplete (the profiled run did not finish), so this exits 4 ...
rc=4
```
The same profile pointed at the real manifest works first time:
```
$ bento profile ./src/build.sh --out build.manifest.yaml </dev/null
hello
4 src/build.sh
[bento] wrote build.manifest.yaml ...
$ cat build.manifest.yaml
read:
- ./src
- ./data/input.txt
write:
- ./build
```

**Why it bites:** the suggested command runs the script from `src/` instead of the manifest's
`workdir: .`, so every relative path resolves wrong. The user gets a proposal for the wrong
paths (`src/build`, never `data/`), a second manifest in `src/` that is not the one they run,
and exit 4 telling them to "fix the run". They never learn that `--out` is how you profile
against an existing manifest. `profile --help` doesn't say that either.

**Fix:** have the failed-run hint print `bento profile <entrypoint> --out <this manifest>`,
which honours `workdir:` and merges into the file the user actually runs.

#### 2. `validate` says a shell script is a compiled binary - Polish

**Persona:** new developer, reading `validate` output for a hand-written manifest.

**Transcript:**
```
$ head -1 src/build.sh
#!/bin/sh
$ bento validate build.manifest.yaml
entrypoint:   ./src/build.sh
interpreter:  (none - the entrypoint is a compiled binary)
```

**Why it bites:** the claim is false, so it undercuts the output around it. When the user
later profiles, the interpreter gets silently pinned to `/bin/sh` ("the manifest named
interpreter "", but this run profiled under "/bin/sh"").

**Fix:** say "(none - executed directly; a shebang, if any, picks the interpreter)".

#### 3. Re-profiling adds `env: [HOME, LOGNAME, USER]` without mentioning it - Polish

**Persona:** new developer, widening their manifest with profile.

**Transcript:**
```
$ bento profile ./src/build.sh --out build.manifest.yaml </dev/null
... [change summary covers the widening, the interpreter, and the dropped approval; no mention of env]
$ cat build.manifest.yaml
env:
- HOME
- LOGNAME
- USER
```

**Why it bites:** the README says profile "says what it changed". This change moves the
script's `HOME` from `/tmp` to the real home directory, and `approve --yes` stamps it
with nothing pointing it out.

**Fix:** add the env names to profile's change summary.

- `HOME` pointed at `scratchpad/ops/home` for every run; the real repo and config were not touched

### Persona and journeys

Operator: runs bento for a team and gets asked "why did this fail". Knows the README and
`--help`, and reads source only to explain a finding.

| Goal | Result |
|---|---|
| (a) write and change manifests from the docs alone | Done. README "Manifest Reference" covers every key the parser accepts (I diffed it against the yaml tags). bento has no global config file or user-facing env vars besides the manifest, so nothing else needs a reference. | (b) trigger proxy, gate and run failures and read the output | Proxy denials are good: 403 (no rule), 400 (plain http) and wrong port each name the destination and the next step. OOM via `limits` is named. Hook denials name the cause. Findings 1-3. |

driving the hook. I drove the hook by piping PreToolUse JSON into it.

### Findings

#### 1. Every run with a write grant outside a git checkout says bento "could not read these grants whole" - Friction

**Persona:** operator reading the output of a successful run, or of a failed one to find out why.

**Transcript:**
```
$ cat m.yaml
entrypoint: /bin/true
write: [./w]
$ git -C w rev-parse --git-dir
fatal: not a git repository (or any of the parent directories): .git
$ bento run m.yaml --allow-unapproved; echo rc=$?
[bento] sandbox engaged: 14 credential/host-service path(s) shielded (0 hidden, 14 discarded); --json lists them
[bento] note: bento could not read these grants whole this run - git did not
[bento] answer where they run their hooks, or they stopped answering at all:
[bento]   ".../scratchpad/ops/plain/w"
[bento] a denial is the script's own error to report, and does not change its exit code:
...
rc=0
```
The same note shows up on the v0.3.1 binary, and on `examples/probe/grants.manifest.yaml`
when the example is copied out of the repo. It does not show up inside the git checkout.

**Why it bites:** for a directory that is simply not a git repository, the note reads as a
partial failure ("could not read these grants whole", "stopped answering at all"). An
operator looking for why a run failed follows it first. Seeing it on every clean run
teaches them to skip it, including on the day it is real.

**Fix:** treat "not a repository" as resolved with no hooks. Print the note only when git
errored or timed out, and say which of the two happened.

#### 2. The hook's stale-approval denial tells you to pass a flag the hook rejects - Friction

**Persona:** operator whose agent's Bash calls all started getting denied after someone edited `agent.manifest.yaml`.

**Transcript:**
```
$ sed -i 's/^exec: all/exec: none/' agent.manifest.yaml
$ echo "$payload" | bento hook claude-code .../proj/agent.manifest.yaml
{"hookSpecificOutput":{..."permissionDecision":"deny","permissionDecisionReason":"bento: .../agent.manifest.yaml:
 refusing to run: the manifest's permissions changed since it was approved; ... - `bento approve` names them where
 this host recorded the last approval - re-review it there, or pass --allow-unapproved"}}

$ echo '{}' | bento hook claude-code --allow-unapproved .../agent.manifest.yaml
{"hookSpecificOutput":{..."permissionDecision":"deny","permissionDecisionReason":"bento hook claude-code is misconfigured: unknown flag: --allow-unapproved"}}
$ bento hook claude-code --help | sed -n '/Flags/,$p'
Flags:
      --allow   answer allow rather than ask, ...
```

**Why it bites:** the reason is written for `bento run`. Read inside the hook, it offers a
bypass that does not exist there. If the operator adds the flag to settings.json, every
Bash call is then denied with "misconfigured", so one outage turns into a second one.

**Fix:** in the hook's deny reason, drop the `--allow-unapproved` clause and keep only
"re-approve with `bento approve <path>`".

#### 3. The suggested "see what it touches" command profiles the wrong thing and cannot write its output - Friction

**Persona:** operator following bento's own advice after a run failed or egress was refused.

**Transcript:**
```
$ bento run n.yaml -- 'curl -sS -o /dev/null https://example.org'     # entrypoint: /bin/sh, args: [-c], extra_args
curl: (56) CONNECT tunnel failed, response 403
[bento] the egress allowlist refused these destinations - no network rule covers them:
[bento]   "example.org" port "443"
[bento] ... To rediscover them, profile with egress forwarded -
[bento]   bento profile "/bin/sh" --allow-network

$ bento profile "/bin/sh" --allow-network < /dev/null
[bento] profiling /bin/sh under default-deny (egress allowed)...
bento: bento rewrites the manifest through a temporary file in /usr/bin, so it needs write and
search permission on that directory, not only on the manifest: open /usr/bin/.bento-approve-723692024: permission denied
```
A script exiting non-zero prints the same shape: `To see what it actually touches: bento profile "/bin/sh"`.

**Why it bites:** the hint is built from the entrypoint alone. It drops the manifest's
`args` and the run's extra args, so it would profile a bare shell rather than the command
that failed. It also omits `--out`, so the draft is written next to the entrypoint, which
here is `/usr/bin`. When the entrypoint is a system binary, which is the shape the agent
manifest uses, following the advice gets you an unrelated permission error.

**Fix:** build the hint from the run: pass the manifest's args (and any extra args) through,
and add `--out <manifest path>` so profile merges into the manifest that just failed.

#### 4. validate and approve warn that a run can rewrite its own manifest, which v0.4.0 prevents - Friction

**Persona:** operator (or their approver) reading approve's "Worth a second look" before stamping.

**Transcript:**
```
$ bento approve --yes w.yaml        # write: ["."], manifest sits in "."
  - write: ".../ops/repo" covers the manifest itself, so the script can rewrite the policy that
    governs it - and the stamp you are about to write.
$ bento run w.yaml                  # script: echo "# pwn" >> .../w.yaml
/usr/bin/dash: 1: cannot create .../repo/w.yaml: Read-only file system
$ tail -1 w.yaml
  approves: 1a15c0e7...
```
CHANGELOG 0.4.0: "A run can no longer rewrite the manifest it runs. ... The manifest is bound read-only."

**Why it bites:** the callout warns about a risk that `run` now blocks. An approver either
turns down a normal checkout-wide agent manifest (this is the layout `examples/agent`
recommends) or learns that the callouts can be wrong and trusts the rest of them less.

**Fix:** remove the callout, or reword it to what is still true (the manifest is bound
read-only for the run, so check that nothing else writes it).

### Observation (upgrade, not a finding)

A manifest approved under v0.3.1 with `write: ["."]` over a checkout that contains `.claude/`
wrote `.claude/settings.json` under v0.3.1 and gets `Read-only file system` under v0.4.0. The
stamp is still `current`, so nothing flags the change before the run. This is the documented
policy (SECURITY.md: "Adding a shield is not breaking"), and the 0.4.0 CHANGELOG names this
exact shield. The run summary only says "outside the manifest's write: grants, or a shielded
path inside one" and does not name the path. `--json` does name it
(`{"path": ".../repo/.claude", "kind": "read-only"}`), and the summary says so ("--json lists
them"). The operator gets there, but has to make one extra run to do it.

## UX audit 2026-09-25 - persona: QA / contributor verifying a release

### Environment

- Linux 7.0.0-28-generic amd64, go1.27.0, gcc at /usr/bin/cc, bwrap at /usr/bin/bwrap,
  firejail + /etc/firejail and /etc/apparmor.d present, `kernel.apparmor_restrict_unprivileged_userns=1`
  (bwrap still builds sandboxes here). govulncheck not on PATH (the Makefile `go run`s it pinned);
  golangci-lint 2.12.2 on PATH, but the Makefile `go run`s the pinned v2.13.2.
- Fresh clone of c3647fa (v0.4.0) at `scratchpad/qa/bento`, failure injection in a second clone `scratchpad/qa/b2`.
- **`make check` passed**: rc=0, 3m51s wall, every leg ran (vet, crossbuild, bentoprobe, lint, test,
  race, bench, layering, audit, examples, vuln), with network.

Journeys run: `make check` as documented; `make examples` with no working bwrap; `make test`
with no working bwrap; `make race` with no C compiler; `make vuln` offline (proxy refused) and
with `GOPROXY=off`. Unrun: a host with no firejail/AppArmor profiles (needs root to remove them),
the CI workflow itself.

Verdict: the gate runs as documented on a well-provisioned host, and the race and vuln failures
name their cause. The real gap is that the gate's "a skip is a failure" discipline stops at
`make test` and `make race`: `make examples` still passes green having skipped its sandbox runs.

### Findings

#### 1. `make examples` (and so `make check`) passes green with every sandboxed example run skipped - Blocker

**Persona:** QA verifying a release on a host whose bwrap cannot build a sandbox.

**Transcript:**
```
$ printf '#!/bin/sh\nexit 1\n' > fakebin/bwrap; chmod +x fakebin/bwrap
$ PATH=$S/fakebin:$PATH make examples; echo rc=$?
==> Verifying example modules...
SKIP: the agent example needs a host bubblewrap can build its sandbox on
ok  	bentoembed	0.030s
OK: example builds and tests against bento's public API only
OK: an unapproved manifest is refused by default
SKIP: demo run needs a host bubblewrap can build its sandbox on; the API checks above still ran
SKIP: the quick start needs a host bubblewrap can build its sandbox on
ok  	bentosupervise	3.848s
...
✓ Examples verified!
rc=0
$ BENTO_REQUIRE_TEST_DEPS=1 PATH=$S/fakebin:$PATH make examples | grep -E 'SKIP|✓'
SKIP: the agent example needs a host bubblewrap can build its sandbox on
SKIP: demo run needs a host bubblewrap can build its sandbox on; the API checks above still ran
SKIP: the quick start needs a host bubblewrap can build its sandbox on
✓ Examples verified!
$ grep -l BENTO_REQUIRE examples/*/verify.sh
(nothing)
```

**Why it bites:** the Makefile and CONTRIBUTING both say a skipped behavioural test must fail the
gate (that is what `BENTO_REQUIRE_TEST_DEPS` is for), so a QA reading "Examples verified" concludes
the agent hook path and the quick start actually ran. Three of the examples' end-to-end runs can
be skipped and the release still reads "All quality gates passed cleanly". In `make check` the
earlier `make test` leg would fail first on such a host, but `make examples` run alone - which
CONTRIBUTING lists as its own target - certifies nothing.

**Fix:** have each `verify.sh` exit non-zero instead of `SKIP ... exit 0` when
`BENTO_REQUIRE_TEST_DEPS` is set, and set it in the `examples` target the way `test` and `race` do.

#### 2. README says `make test` skips without bwrap; it fails with 166 test failures and no hint why - Friction

**Persona:** contributor on a host with no usable bwrap, following README "Development & Testing".

**Transcript:**
```
$ sed -n 612,613p README.md
make test       # unit and integration tests (sandbox tests skip if bwrap/userns are missing;
                # the denylist parity tests also want firejail and its apparmor profiles)
$ PATH=$S/fakebin:$PATH make test; echo rc=$?
--- FAIL: TestProfileForwardsDenyPaths (0.00s)
    profile_linux_test.go:144: the bwrap sandbox cannot be built on this host (user namespace or /proc mount refused)
...
FAIL	github.com/whiskeyjimbo/bento/backend
FAIL	github.com/whiskeyjimbo/bento/cmd/bento
FAIL	github.com/whiskeyjimbo/bento/internal/launcher
FAIL	github.com/whiskeyjimbo/bento/internal/linux
make: *** [Makefile:107: test] Error 1
rc=2
$ grep -c -- '--- FAIL' faketest.log; grep -c BENTO_REQUIRE faketest.log
166
0
```

**Why it bites:** the failing behaviour is the intended one (CONTRIBUTING describes it correctly),
but the README promises a skip, and the failure text never says that the gate deliberately turned
a skip into a failure or how to run a plain `go test` locally. A contributor reads 166 failures as
"I broke something" or "the release is broken".

**Fix:** correct the README comment to match CONTRIBUTING ("fails if bwrap/userns/firejail are
missing; plain `GOWORK=off go test ./...` skips them"), and have the require-deps failure message
name `BENTO_REQUIRE_TEST_DEPS`.

#### 3. The documented prerequisites omit python3 and the AppArmor userns sysctl the gate relies on - Friction

**Persona:** QA provisioning a fresh host from CONTRIBUTING "Development setup".

**Transcript:**
```
$ sed -n 27,29p CONTRIBUTING.md
You need Go (see the version in go.mod) and, on Linux, `bubblewrap`
with unprivileged user namespaces enabled. `make race` needs a C toolchain for
the race detector.
$ grep -n -i -E 'python|apparmor_restrict|sysctl' CONTRIBUTING.md
(nothing)
$ head -14 examples/agent/verify.sh | grep python3
if ! command -v bwrap >/dev/null 2>&1 || ! command -v python3 >/dev/null 2>&1; then
	echo "SKIP: the agent example needs bwrap (bubblewrap) and python3" >&2
$ grep -n -E 'apt-get install|apparmor_restrict' .github/workflows/gate.yml
45:        run: sudo apt-get update && sudo apt-get install -y bubblewrap firejail apparmor
52:          if [ -e /proc/sys/kernel/apparmor_restrict_unprivileged_userns ]; then
53:            sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0
```

**Why it bites:** CI's gate installs firejail + apparmor and flips the Ubuntu 23.10+ sysctl; the
contributor doc names only bwrap (firejail appears later, in a bullet). Without python3 the agent
example silently skips (finding 1). The reader learns the real list only by reading gate.yml.

**Fix:** one prerequisites list in CONTRIBUTING: go, bubblewrap, firejail, apparmor profiles,
python3, a C compiler, network, and the sysctl note (or a pointer to gate.yml's setup step).

#### 4. The documented gate lists drift from what `make check` runs - Polish

**Transcript:**
```
$ grep -n 'make check' CONTRIBUTING.md
38:make check   # the full gate: vet, crossbuild, lint, test, race, audit, examples, vuln
$ make help | grep check
  check        Run all quality gates (vet, crossbuild, bentoprobe, lint, test, race, bench, layering, audit, examples, vuln)
```
CONTRIBUTING's "Useful targets" also omits `layering`, `bench`, `bentoprobe`; the README's list omits
`bench` and `bentoprobe` and still calls itself "every gate above".

**Why it bites:** a QA running the parts individually to bisect a red `check` misses three legs.

**Fix:** point both docs at `make help` instead of hand-copied lists, or add the three targets.

#### 5. The green audit leg prints ~1,300 lines of review output - Polish

**Transcript:**
```
$ sed -n '/denylist audit/,/Denylist audit complete/p' check.log | wc -l
1299
glob for review - verify bento's named instances cover it: /home/u/.*.bak [AppArmor private-files abstraction]
...
no unclassified in-scope gaps: every secret/exec upstream shield is covered or excluded
1248 out-of-scope gap(s) skipped (upstream's privacy/other-app/system scope), by section:
```

**Why it bites:** on a passing run the verdict line is buried in a wall of "for review" text, so a
QA scrolling `make check` output cannot tell at a glance whether the audit wants action.

**Fix:** print the verdict and counts in the gate; put the per-path lists behind a verbose flag.

#### Checked and fine

- `make race` with no compiler: `cgo: C compiler "/nonexistent/cc" not found ... FAIL ... [build failed]` - names the cause.
- `make vuln` offline: `Get "https://proxy.golang.org/...": proxyconnect tcp: dial tcp 127.0.0.1:9: connect: connection refused`, after a banner that says it fetches; and vuln is the last leg of `check`, so every other leg has already reported. Raw Go error, but clear enough given CONTRIBUTING says it needs network.
